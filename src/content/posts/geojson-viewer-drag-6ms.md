## 太长不看

| 项目 | 内容 |
|---|---|
| **现象** | 拖动地图时"拖一下卡一下"；一次拖动（6 次移动）的会话中位 **5,671 ms**，松手后画面还要再等几百毫秒 |
| **单帧的账** | 一帧 = 清空 462 ms + 找候选 0.6 ms + 画 392 ms。**清空比画还贵** |
| **根因** | 每个 `MouseMove` 都 `Children.Clear()` + 从头画 8,531 个图元；一帧上秒级，事件在队列里越排越长 |
| **正解** | 拖动时**不重画**：图元留着，只改一个 `RenderTransform`；再挂 `BitmapCache` 让"改变换"真的只是搬一张图；再**多画一屏余量**，让平移永远不出界 |
| **数据** | 拖动一帧 **1,167 ms → 6.0 ms**（195×）；滚轮一格 **1,400 ms → 173 ms**（出画面），151 ms 后补细 |
| **代价** | 位图缓存占 9 屏（内容横竖各 3 屏，1,105 × 674 × 9 × 4 ≈ 27 MB）；放大/换数据仍必须重画；拖动中画的是粗版（无边界），松手 250 ms 后补细 |
| **最大的教训** | "只改变换"在 WPF 里**不是免费的**。图元不是位图，`RenderTransform` 只换了矩阵，渲染线程照样要逐图元重新栅格化——单独用它比重新画还慢（2,528 ms vs ~800 ms）。真正让它是"搬图"的，是 `BitmapCache` |

## 一、原来是怎么样

数据是 Natural Earth 的省级行政区：**4,595 个对象 / 8,531 个部件 / 1,290,065 个点**，画布 1,105 × 674。

用探针（一个记录"鼠标按下那一刻 → 这一帧真的上屏"的独立小程序）量出来的旧程序：

| 指标 | 值 |
|---|---|
| 拖动一帧"请求 → 上屏" | **1,167 ms**（中位） |
| 其中 UI 线程（清空 + 建图元 + 挂进画布） | 429 ms |
| 其中渲染线程（光栅化 + 合成） | 738 ms |
| 帧周期（一次拖动内，相邻两帧的间隔） | 1,942 ms |

"帧周期 1,942 ms"意味着：你不拖了，队列里还堆着好几帧要画。用户感受到的就是"松手之后画面还在追"。

顺带一提，三代方案的对比在[第一篇文章](/posts/wpf-canvas-resize-geobounds)里已经放过：画布相关的 bug 修完、每个对象一个 `Shape` 的老路子上，一帧就是几百毫秒到一秒。**这次要改的不是"画得快一点"，而是"根本不画"。**

---

## 二、每帧图像怎么被画出来？

在动手之前，先给一帧装上三只秒表：清空、找候选、画。

| 阶段 | 1× （全幅） | 8× （只看一小块） |
|---|---|---|
| `Children.Clear()` | **462.1 ms** | 462.1 ms |
| 空间索引找候选 | 0.6 ms | 10.8 ms |
| 画候选 | 391.7 ms | 15.0 ms |

我们重点关注两个数字：

1. **清空 8,531 个 `UIElement` 要 462 ms**，比画还贵。`Clear()` 不只是"把数组清掉"，它要解挂每个图元、让布局失效、通知渲染线程丢掉对应的那部分渲染数据。
2. **画的开销与"画多少"强相关，与"离得多近"无关**。8× 时只要画 77 个部件，画只要 15 ms —— 空间索引（上一篇的主角）已经把"该画哪些"解决得很好了，剩下 462 ms 是**每帧都要重来一遍**的固定成本。

所以最贵的那一笔，恰恰是"每帧都从头来"这个**结构**。只要还"清空重画"，索引再快也只能把 462 + 392 压到 462 + 15。

## 三、第一版：只改变换 —— 反而更慢

最朴素的想法：既然只是拖动，为什么要把 8,531 个图元扔掉再画一遍？把它们留着，平移整块内容就行了。

```csharp
// MapCanvas 只有这一个子元素：所有图元挂在 _content 上
MapCanvas.Children.Add(_content);

// 平移时只改它
_content.RenderTransform = new TranslateTransform(dx, dy);
```

写完，量了一下：

| 方案 | 一帧"请求 → 上屏" |
|---|---|
| 清空 + 重画（原方案） | ~800 ms |
| 只改 `RenderTransform` | **2,528 ms** |

**比重新画还慢 3 倍。** 这一个方案明显不通，但它揭示了一件关于 WPF 的重要事实：

> `RenderTransform` 改的是"这个元素挪到哪里显示"，不是"摆放什么东西"。图元本身没有变成像素——`Shape` 仍是矢量对象，渲染线程每帧仍要把这棵子树里每个图元重新栅格化成像素。

也就是说：省掉了 UI 线程的 429 ms，却把渲染线程那 738 ms 原样留下了——甚至更糟。因为那 8,531 个 `Shape` 是 8,531 个子元素，带着变换时 WPF 不会复用上一帧的像素，而是把整棵子树重新栅格化一遍（每一条描边都要重新生成抗锯齿的环形几何）；而且这一次是 8,531 个子元素各自带着新位置重新提交渲染数据，失去了"一次统一处理一批"的余地。变换只换了矩阵，没有改变"它们仍然是矢量"这个事实。至于 738 → 2,528 这 3 倍具体花在哪儿，当时没有拆到底——只记了现象和它引出的结论。

**教训：在 WPF 里，"少做点工作"和"把工作挪个地方"是两件事。只改变换，挪的是工作量，不是成本。**

## 四、位图缓存：把"每帧重画"换成"搬一张图"

要让"改变换"真的等于"搬一张图"，得明确告诉 WPF：这块内容你可以光栅化一次存起来。

```csharp
_bitmapCache = new BitmapCache(VisualTreeHelper.GetDpi(this).DpiScaleX);
_content.CacheMode = _bitmapCache;
```

`BitmapCache` 的语义是：这个 Visual 的渲染结果**缓存成一张位图**，之后变换、裁剪、合成都作用在那张图上。

加上它，同一个测量变成：

| 方案 | 一帧"请求 → 上屏" |
|---|---|
| 只改 `RenderTransform` | 2,528 ms |
| 改变换 + `BitmapCache` | **6.1 ms** |

三个需要注意的细节：

1. **缓存分辨率必须按屏幕 DPI 光栅化。** `BitmapCache()` 无参构造默认按 1.0 光栅化，放到 1.5× 的屏幕上会被放大 1.5 倍，边缘糊成一片。所以传 `DpiScaleX`。
2. **平移量取整到设备像素。** 小数像素的平移会让缓存被重采样，肉眼看着"发虚"，在像素比较里表现为"整张图差一点点"。
3. **缓存会随内容自动失效。** 这是好事（正确性有保证），但也意味着：**只要内容变了（缩放、换数据、换投影），缓存就重建，一笔都省不下来**。这一条直接决定了第五、七节的做法。

## 五、多画一屏：让"重画"变成罕见事件

缓存解决了"内容不变时的平移"，但还剩一个问题：**内容什么时候不变？**

1× 全幅时，整个地球都在视野里，怎么平移内容都还在。可一旦放大，视野里只有一小块：往边上拖，拖出视野的部分本来就没画，屏幕上会露出白边。

最直接的办法是"每次拖出边界就重画一帧"。测了一下，1.5× 下大约每 454 像素就撞一次，每次要 1.16 秒 —— 体验上就是"拖几下、卡一下"。

改法很朴素：**画的时候多画一圈。**

```csharp
// 拖动的那几帧：查询范围 = 视口 + 一屏，内容画布也撑大同样尺寸
var marginX = _dragging ? MapCanvas.ActualWidth : 0;
var marginY = _dragging ? MapCanvas.ActualHeight : 0;
```

于是拖动帧画的内容是 **3 屏宽 × 3 屏高**，平移在 ±一屏之内都有东西可看。

为什么是"一屏"而不是更多？因为**鼠标拖不出屏幕**：一次拖动最多移动一屏。铺一屏余量，一次拖动里就永远不用重画；铺两屏，只有内存翻倍。

实测：1.5× 下"撞边界重画"的距离从 454 px 变成 1,079 px（就是余量本身），一次拖动里重画次数从约 2 次变成 0。

## 六、什么时候必须重画：判据要用屏幕位移

"还在余量里"这个判断，一开始写成了"当前数据包围盒是否落在上一帧画过的那块里"。结果在 1.5× 上立刻出两个 bug：

1. **整体偏右下 480 像素。** 只把 `_content` 的 `Width/Height` 撑大了，没把原点挑到 `(-margin, -margin)`。撑大的方向错了，整块内容就偏了。
2. **"明明都画完了还重画"。** 数据包围盒在放大后会变（每帧重新算），用它判包含，越放越不成立。

正确的判据只有一条：**屏幕上的位移有没有超过余量。**

```csharp
/// <summary>能不能"只平移"：图层/投影/缩放/视口都没变，且视野仍落在上一帧画过的范围里。</summary>
private bool CanTranslateOnly()
{
    if (!_hasFrame || !ReferenceEquals(_layer, _lastLayer)) return false;
    if (_settings != _lastSettings) return false;                    // 投影变了，屏幕坐标全变
    if (!Same(_bounds.Zoom, _lastZoom)) return false;                // 缩放变了，顶点必须重算
    if (!Same(_bounds.ViewportWidth, _lastViewW) || !Same(_bounds.ViewportHeight, _lastViewH)) return false;
    if (_lastFrameCoarse && !_dragging) return false;                // 上一帧是粗版，得补细

    // 平移量换算成设备像素再比；减掉点半径，否则压边的点会被裁掉半个
    return Math.Abs(_bounds.PanX - _drawPanX) <= _drawnMarginX - MaxPointRadiusPx
        && Math.Abs(_bounds.PanY - _drawPanY) <= _drawnMarginY - MaxPointRadiusPx;
}
```

`PanX/PanY` 是 `GeoBounds` 里唯一的"内容整体挪了多少"（[第一篇文章](/posts/wpf-canvas-resize-geobounds)的主角），它本来就是屏幕像素量，所以这里可以直接拿来比。减去 `MaxPointRadiusPx`（点的最大半径 26 px）是因为：包围盒刚好在视野外一点点的对象，它的点/线仍有一半压在画面里。

## 七、缩放：靠"先粗后细"，但做法在另一篇

缩放和拖动有一处本质不同：**所有顶点的屏幕坐标都变了**，没有"只挪一下"的余地。它的解法是"先出一帧粗的、空闲了再补细"。但这需要合并渲染提供的"粗版通道"，所以完整做法（4 px 抽稀、不描边、滚轮一格 1.4 s → 173 ms 的实测）写在《把 8,531 个控件合成 1 个》那一篇里，不在本篇。

## 八、最终数字与代价

| 场景 | 之前 | 现在 |
|---|---|---|
| 拖动每帧 | 1,167 ms | **6.0 ms** |
| 拖动中撞余量重画（1.5×） | 1,400 ms | 103 ms（粗版） |
| 松手 | 立刻全量重画一次（~1 s） | 不画；250 ms 空闲后补一帧细版 |
| 滚轮缩放（到出画面） | 1,400 ms | **173 ms** |
| 画面最终效果 | 细版 | 细版（拖动中暂时是粗版） |

我们失去了什么：

- **内存**：位图缓存 = 9 屏 × 4 字节（横竖各 3 屏：1,105 × 674 × 9 × 4 ≈ 27 MB），加缓存本身的开销。
- **放大/换数据仍必须重画**：这不是新方案的缺点，是问题本身的固有成本（几何与比例绑定）。
- **拖动中看不见边界**：粗版只填色不描边。松手 250 ms 后恢复。
- **像素不是完全一致**：余量帧与"复位后重画"之间有 2.7% 的像素差（最大通道差 20），全部落在边缘——位图平移按设备像素取整后整张搬过去，边缘的亚像素覆盖和重新光栅化差一点点。不是位移，肉眼不可分辨。

## 九、可以复用的小结

> [!TIP] 让"拖动"变快的四条
> 1. **先看一眼"每帧的固定成本"。** 如果它是"清空 + 重建全部图元"，那不管你怎么优化那块，规模一大就完蛋。先问：这一帧里有多大比例是**每帧都要重来一遍**的？
> 2. **改变换 ≠ 省渲染。** 在 WPF（以及任何保留模式的 UI）里，矢量图元每次合成都要重新光栅化。要让变换真的便宜，必须把它变成**位图**（`BitmapCache`、`RenderTargetBitmap`、或自己画到一张图上）。
> 3. **别求"每次拖动都精确重画"，求"少重画"。** 多画一圈余量（按"鼠标能拖多远"定尺寸）、粗版先行、空闲补细 —— 这三件事都是拿"一点点精度"换"数量级"，而且用户根本看不见。
> 4. **判据要用屏幕量，不要用数据量。** "内容有没有出界"是屏幕问题；用数据包围盒去判，缩放一变就失真。屏幕位移本来就是像素，判起来还更快。

## 附录：为什么"地图里"拖会卡，"地图外"拖很滑

在某次实机测试中，我们发现：鼠标在地图形状上拖动会卡，拖到空白处就非常丝滑。

原因不在我们画的任何东西，而在 WPF 的输入命中测试：指针落在某个 `Shape` 上时，要路由一条 `MouseMove` 给"最上层的那个元素"，WPF 得先逐个测这些图元、还要算几何包含（俄罗斯、南极洲那种几万点的多边形）。实测：落在图形上 **28 ms/次（P90 687 ms）**，落在空白处 **0.002 ms**——差四个数量级。

我们从来不需要 WPF 帮忙判"点到了哪个对象"（那是我们自己的 `HitTester` + 空间索引干的活），所以一行就够了：

```csharp
_content.IsHitTestVisible = false;   // 只让 WPF 测到 MapCanvas 这一层
```

这一条成为了我们发现探针数据错误的提示：探针日志里 UI 线程一行看不出耗时，帧周期却很长——那笔钱花在输入命中测试里，账单记在下一个事件头上。

## 附录 2：为什么不自己管一张位图

`BitmapCache` 不神秘，等价的做法是：把内容画进 `RenderTargetBitmap`，用一个 `Image` 显示它，平移只改 `Image` 的 `Canvas.Left/Top`（这一步零成本，连变换都不用）。

真写起来会多出四件事：

1. **失效点要自己穷举**：缩放、换数据、换投影、窗口尺寸变化、DPI 变化……每一处都得记得"重建那张位图"。漏一处就是画面停在旧状态，而且不报错。
2. **DPI**：屏幕挪到 150% 缩放的显示器上，位图会被拉伸糊掉，得按新 DPI 重新光栅化。
3. **绘制上下文**：`RenderTargetBitmap.Render(visual)` 要求那个 visual 已经完成布局（`Measure`/`Arrange` 过），否则画出来是空的——先用一个没进树的 `Canvas` 试过，整张图空白，PNG 只有 3 KB。
4. **合成**：`Image` 参与布局，会引入自己的测量/排列成本；`BitmapCache` 是在合成层生效的，不碰布局。

结论：自己管位图只换来一个自由——精确控制"什么时候重画"；代价是"什么时候该重画"这件事要你全权负责。而地图控件要的恰好就是"内容一变自动失效"，所以没有自己造。
下一篇处理剩下那笔最贵的账：1× 全幅时 8,531 个 `UIElement` 的清空与重建，以及把它们合成一个 `DrawingVisual` 之后，重绘为什么从 807 ms 掉到 96 ms。
