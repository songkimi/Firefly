## 太长不看

| 项目 | 内容 |
|---|---|
| **现象** | 拉窗口时地图内容会自己放大/缩小；且缩小时表现为"上下各裁掉一半"的**居中裁剪** |
| **根因** | `SetViewport()` 一次做了两件事：**记录画布尺寸** + **重算 fit 比例**。画布尺寸每次 resize 都变，于是 fit 比例也跟着变 → 内容被缩放 |
| **正解** | 按职责拆开：`SetViewport()` 只记尺寸并补偿平移；**只在 `Reset()`（打开文件 / 切投影）里做 fit** |
| **副产品** | 拉窗口导致的裁剪方向是必然的（不然就得缩放）。必须选一边"钉住"，用平移量补半个尺寸差即可 |
| **公式** | 让"同一个屏幕像素反解出的地理坐标不变"，代数化简后得到 \(panDelta = \dfrac{旧宽 - 新宽}{2}\)——地理量 \(x\)、缩放 \(k\)、屏幕量 \(s_x\) 全被消掉（见附加问题 §1.3） |
| **数据** | 画布 1120×720 → 920×580：`BaseScale` 39.833869 冻住、北京↔广州 679.84px 不变、左上角底下压着的数据 `(103.3107, 40.7021)` 一点没动 |
| **最大的教训** | 别用"某个屏幕坐标前后相等"当不变量判据。屏幕坐标系的原点会随画布一起变，那个坐标**本来就该变**；要盯的是"同一个屏幕位置反解回地理空间还等不等" |

## 一、背景：这个模型长什么样

项目是一个迷你 GeoJSON 查看器（C# + WPF），画布就是一块 `Canvas`，坐标流水线是两步：

```
经纬度 ──Projection.Project()──▶ 平面数值 ──GeoBounds.ToScreen()──▶ 屏幕像素
```

`GeoBounds` 负责后一步（fit / zoom / pan），它是纯计算类，不认识 WPF，只管一件事：**给我一个平面坐标，我告诉你画在画布的第几个像素**。核心公式只有一行：

```csharp
// 屏幕坐标 = 画布中心 + 平移量 + (数据 − 数据中心的偏移) × 缩放比例
screenX = _viewportWidth  / 2 + _panX - (x - _centerX) * _baseScale;
screenY = _viewportHeight / 2 + _panY + (y - _centerY) * _baseScale;   // y 轴朝下，符号不同
```

> 这里已经是修好之后的版本了。注意 `_panX` 是**唯一**能表达"内容整体挪了多少"的状态；这个点在后面"为什么非要走 pan"那一节会变成关键。

其中 `_baseScale` 是"一个数据单位画多少像素"，也叫 fit 比例——**问题就出在这个值的生命周期上**。

---

## 二、我们看到的两个现象

### 现象 1：拉窗口，内容跟着缩放

打开一个文件后，地图会自动 fit 到画布（全部可见、四周留 20px 边距）。这时如果拉大窗口，地图内容**也会跟着放大**；拉小窗口，内容跟着缩小。

当时能发现一个很明显的问题：

> "原尺寸能包容所有的点，但当我将画布缩小到那个点不再被画布覆盖了的时候，强制改动了我的缩放使我能看到所有的点了。"

这句话点出了本质：我们**并不想**让内容缩放，是程序"擅自"帮用户重新 fit 了一次。

### 现象 2：缩小窗口，内容被"居中裁剪"

如果内容尺寸不变，那么画布变小后，必然有一部分内容要消失——**从哪边消失才是问题**。

经过多次观察：

> "现在的状态似乎是窗口被重画，但给人的感觉是'居中裁剪'，比如我屏幕高缩小 40，但实际的表现是上裁 20px，下裁 20px。我想不通为什么会这样了，我猜想我们需要一个定点，正如钉住画板与画布的钉子"

这个直觉是对的：**需要一个定点**。而"上下各裁 20"说明当时的定点是**画布中心**——因为公式里那一项是 `_viewportHeight / 2`，视图中心永远锚在画布正中，高度从 720 变 680，中心从 360 变 340，四周自然等量消失。

## 三、猜过的方案，以及哪些是错的

| # | 方案 | 结果 |
|---|---|---|
| A | 在 `OnCanvasSizeChanged` 里**删掉** `SetViewport` 调用 | ❌ 内容确实不缩放了，但画布尺寸记不进去了。而 `ToScreen` 里的"视图中心"就是 `_viewportWidth / 2`，尺寸停在打开文件那一刻 → **鼠标准星偏 (旧W−新W)/2 = 100 像素**，悬停和缩放锚点全错 |
| B | 保住 `SetViewport`，额外维护一个"冻结的 fit 比例" | ⚠️ 能工作，但等于同一个字段存两份，状态同步迟早出问题 |
| C | 判断尺寸变化是否超过某个容差，小于则不算 | ❌ 治标：容差内不重算，超过照样跳 |
| D | **按职责拆开 `SetViewport`** | ✅ 最终方案 |

方案 A 迅速执行发现错误，但这正好成为我们优化`SetViewport`方法的契机：**把"记录尺寸"和"重算 fit"拆开**。

## 四、根因

```csharp
// 出问题的版本
public void SetViewport(double width, double height)
{
    _viewportWidth  = width;
    _viewportHeight = height;
    RecomputeBaseScale();   // ← 罪魁祸首：每次尺寸变化都重新算 fit
}
```

`RecomputeBaseScale()` 算的是"把整个数据范围塞进画布、四周留 padding"需要的比例：

```csharp
var usableW = Math.Max(_viewportWidth  - 2 * _padding, 1.0);
var usableH = Math.Max(_viewportHeight - 2 * _padding, 1.0);
_baseScale = Math.Min(usableW / _spanX, usableH / _spanY);   // 取较小值，保证不变形
```

这个式子**必然**把画布尺寸和内容比例绑死——画布小一点，比例就小一点，内容就缩一点。resize 一来就调它，等于每次拉窗口都偷偷替用户重新 fit 一次。

于是两个现象合成一个根因：**"fit" 这件事发生得太频繁了**。

> [!IMPORTANT] 一个前提别漏了
> 下面所有推导都默认 **\(k\) 在这次尺寸变化前后是同一个值**。这正是修复的核心：`BaseScale` 被冻住，所以 resize 不影响它。反过来，如果 `BaseScale` 跟着画布一起变，下面 §6.3 里"两边同乘 \(k\) 消分母"那一步就不成立了。
> 另外 \(k\) 里其实含着 `Zoom`，滚轮一动它就变——所以补平移这件事**必须发生在 resize 之间，不能跨到滚轮之后**。

---

## 五、修法

把 `SetViewport` 的一个副作用拆成两个方法各自的职责：

| 方法 | 什么时候调 | 记画布尺寸 | 算 `BaseScale` | 平移量 |
|---|---|---|---|---|
| `SetViewport(w, h)` | 窗口尺寸变了 | ✅ | ❌ 不碰 | 补半个尺寸差 |
| `Reset(w, h, padding)` | 打开文件 / 切投影 | ✅ | ✅ 重新 fit | 归零 |

```csharp
// 只记尺寸 + 补偿平移，绝不重算 fit 比例
public void SetViewport(double width, double height)
{
    var panDeltaX = (_viewportWidth  - width)  / 2.0;
    var panDeltaY = (_viewportHeight - height) / 2.0;
    _panX += panDeltaX;
    _panY += panDeltaY;
    _viewportWidth  = width;
    _viewportHeight = height;
}
```

这样：**内容尺寸不变**（`BaseScale` 冻住），**准星不偏**（尺寸照常更新），**看起来还是居中的**（补了半个尺寸差）。

### 为什么偏移量必须是 `pan`？

这正是最后也最为关键的地方：

> "我能理解部分，比如我有一个点坐标为（20，20），画布刚好为（20，20），然后我往右拉画布至 40px，按照原来的算法应该跑到（30，20）去了，但这里算出来相差尺寸为 20 除以 2 为 10，此时将算出来的坐标去掉 10 就回到原坐标了，但为什么要用偏移量 panx（y）来算？"

这里给出对上述代码的解释（如果需要更加严谨的证明，请见**附加的问题**项1），卡住的是"为什么非要改 pan 这个字段"。三个理由：

1. **`ToScreen` 是每帧现算的，屏幕坐标是结果不是状态**。你没有地方"改屏幕坐标"，只能改它的输入；
2. **`_panX` 是公式里唯一代表"内容整体挪了多少"的状态**。半个尺寸差就是一次整体平移，语义完全对上；
3. **如果绕开 pan 在别处减，就得在三处各减一次**——渲染、命中测试、缩放锚点都要各自记得减。同一件事写三处，漏一处鼠标准星就偏了；
4. 附带一个顺序约束：pan **必须在缩放之后加**（公式里中间夹着 `缩放比例 = Zoom × BaseScale`，而 Zoom 随时会被滚轮改），所以它不能并进 `BaseScale` 里。

## 六、附加的问题

### 坑 1：把"屏幕坐标不变"当成不变量（含完整推导）

#### 6.1 先写死两个互相逆运算的转换式

我们的坐标流水线只有两步，写成式子是：

$$
s_x = \frac{W}{2} + panX + k\,(x - c_x) \qquad \text{(1) 地理} \rightarrow \text{屏幕}
$$

把 (1) 移项逆推，就得到反变换：

$$
x = \frac{s_x - \frac{W}{2} - panX}{k} + c_x \qquad \text{(2) 屏幕} \rightarrow \text{地理}
$$

符号含义：

| 符号 | 含义 | resize 前后 |
|---|---|---|
| \(s_x\) | 屏幕像素坐标，单位 px | — |
| \(x\) | 地理坐标（经纬度那一侧） | — |
| \(W\) | 画布宽度，单位 px | 旧 \(W\) → 新 \(W'\) |
| \(panX\) | 横向平移量，单位 px | \(panX_{old}\) → \(panX_{new}\)（**待求**） |
| \(k\) | 缩放系数，单位 px / 地理单位 | **不变**（§4 的修复保证了这点） |
| \(c_x\) | 基准地理中心，固定地理值 | 不变 |

#### 6.2 列约束：同一个屏幕像素，看到的地理点不变

注意约束写在**地理空间**上：

> 窗口 resize 前后，同一个屏幕像素 \(s_x\) 反解出来的地理坐标 \(x\) 必须完全相等。

拿画布左上角那个像素理解：不管窗口怎么拉，"屏幕上第 0 个像素"底下压着的那块地方不能跑。

分别代入 (2)：

$$
x_{old} = \frac{s_x - \frac{W}{2} - panX_{old}}{k} + c_x,
\qquad
x_{new} = \frac{s_x - \frac{W'}{2} - panX_{new}}{k} + c_x
$$

令 \(x_{old} = x_{new}\)：

$$
\frac{s_x - \frac{W}{2} - panX_{old}}{k} + c_x
=
\frac{s_x - \frac{W'}{2} - panX_{new}}{k} + c_x
$$

#### 6.3 代数化简

$$
\begin{aligned}
\frac{s_x - \frac{W}{2} - panX_{old}}{k} &= \frac{s_x - \frac{W'}{2} - panX_{new}}{k} &&\text{两边消掉 } c_x \\[4pt]
s_x - \frac{W}{2} - panX_{old} &= s_x - \frac{W'}{2} - panX_{new} &&\text{两边同乘 } k \ (k \neq 0) \\[4pt]
- \frac{W}{2} - panX_{old} &= - \frac{W'}{2} - panX_{new} &&\text{两边消掉 } s_x \\[4pt]
panX_{new} - panX_{old} &= \frac{W}{2} - \frac{W'}{2} &&\text{移项、整理符号}
\end{aligned}
$$

代入定义 \(panDeltaX = panX_{new} - panX_{old}\)：

$$
\boxed{\,panDeltaX = \frac{W - W'}{2}\,}
$$

**注意第 3 步**：\(s_x\) 被消掉了。这说明这个等式**和 \(s_x\) 取几毫无关系**——屏幕上的任意一个像素都满足它。这就是"整张地图整体平移"与"只钉住一个像素"的分水岭。

#### 6.4 一个公式，两层逻辑

| 层次 | 内容 |
|---|---|
| **约束条件**（为什么要写这个等式） | 地理坐标相等。它把屏幕空间和地理空间绑在一起，没有它根本不知道该列什么方程 |
| **求解结果**（最后乘出来什么） | \(panDelta\) 是**像素**。化简过程中地理量 \(x\)、缩放 \(k\)、屏幕量 \(s_x\) **全部消掉**，只剩画布的新旧宽度 |

所以：

> 地理坐标是用来**定义"什么叫地图没跑" **的，不是用来参与最后的数值运算的。

#### 6.5 最阴的地方：约束写错，代数却给出同一个式子

如果把约束错误地写成"某个锚点的屏幕像素 \(s_x\) 数字不变"，用 (1) 联立：

$$
\frac{W}{2} + panX_{old} + k(x - c_x) = \frac{W'}{2} + panX_{new} + k(x - c_x)
\;\Longrightarrow\;
panDeltaX = \frac{W - W'}{2}
$$

**公式长得一模一样。** 因为两边的 \(k(x - c_x)\) 也抵消了——于是"用错判据"不会立刻暴露。

区别在**约束的语义**：

| | ✅ 地理约束（正确） | ❌ 屏幕约束（错误） |
|---|---|---|
| 要求 | **任意** \(s_x\) 对应的地理 \(x\) 都不变 | 只有**某一个**锚点像素 \(s_x\) 的数字不变 |
| 结果 | 整张地图刚性平移，任意两点地理距离不变 | 其余像素的对应关系无约束，验证上无法推出"无拉伸" |

代数式相同是必然的（两次推导里 \(s_x\)、\(k\)、\(c_x\) 都被约掉了），但**推理方向决定了你怎么写断言、怎么扩展到多锚点**。用屏幕约束推，到了"左上 / 右下 / 中心锚点"这层就分不清该往哪个方向补，符号自然翻车——这就是我前面错四次的心理根源：

> [!WARNING] 被"屏幕坐标不变"带偏后，我连着改错了四版公式
> 1. 把 \((a - a')\) 直接当 pan 增量；
> 2. 给角锚点补了**一整个**尺寸差（探测输出证明越修越偏）；
> 3. \(\frac{W - W'}{2}\) 写成 \(\frac{W' - W}{2}\)；
> 4. 撞上运算符优先级：`(_viewportWidth - width) / 2.0 - _viewportWidth / 2.0`，看着像 \(-560\)，C# 按同级从左到右算成 \(\frac{\frac{1120-920}{2} - 1120}{2} = -460\)，定点直接飞出画布。

#### 6.6 一个必须小心的例外：纵轴不能照抄横轴

上面的推导是**横轴**的 (1) 式，\(W\) 那一项前面是 `+`。纵轴因为屏幕 y 朝下、纬度朝上，项目里的公式是：

$$
s_y = \frac{H}{2} + panY \;\mathbf{-}\; k\,(y - c_y)
$$

**只有这个符号不同**，但推导的中间步骤会跟着变。我用实测数据验一遍（\(H = 720 \to H' = 580\)，\(k = 39.8339\)，\(c_y = 31.6646\)，旧帧左上角底下压着 \(d_y = 40.7021\)）：

$$
\text{旧：} s_y = \frac{720}{2} + 0 - 39.8339\,(40.7021 - 31.6646) = 0 \quad ✓
$$

$$
\text{新：取 } panDeltaY = \frac{H - H'}{2} = 70,\quad
s_y = \frac{580}{2} + 70 - 39.8339\,(40.7021 - 31.6646) = 0 \quad ✓
$$

所以纵轴的增量公式形式上恰好与横轴一致，都是 \(\frac{\text{旧} - \text{新}}{2}\)——但这是**因为 \(+panY\) 与 \(-k(y-c_y)\) 的符号配上 y 朝下刚好抵掉**，不是"照抄横轴就行"。如果有人把纵轴也写成 \(s_y = \frac{H}{2} + panY + k(y - c_y)\)，同一份代数会给出 \(panDeltaY = \frac{H' - H}{2}\)，也就是**符号整个反过来**。

这里正好可以解释最初那个 (20, 20) → 40px 的例子：它其实是**纵轴**场景。屏幕上把高度从 20 拉到 40，点是往下走 y：20 → 30，要把它拉回 20，需要 \(panDeltaY = \frac{20 - 40}{2} = -10\)。横轴同规模的变化算出的是 \(+10\)——所以那个例子里的数字，正好是纵轴公式（负号）的答案。

#### 6.7 用真实数据复核

把 (2) 代进实际值（\(W = 1120 \to W' = 920\)，\(panX_{old} = 0\)，算出 \(panDeltaX = 100\)，\(k = 39.8339\)，\(c_x = 117.3691\)），任取一个新帧上的屏幕位置 \(s_x = 230\)：

$$
x_{old} = \frac{230 - 560 - 0}{39.8339} + 117.3691 = 109.0847
$$

$$
x_{new} = \frac{230 - 460 - 100}{39.8339} + 117.3691 = 109.0847
$$

数值完全一致。再强调一次：**任取 \(s_x\) 都是这个结果**，因为 \(s_x\) 在 6.3 的第 3 步就被消掉了。

#### 6.8 这个推导证明了什么，没证明什么

| 已证明 | 靠什么 |
|---|---|
| 画布内容**整体刚性平移**，不会拉伸、不会旋转、任意两点间地理距离不变 | 6.3 里 \(s_x\) 被消掉 ⟹ 全部像素共用同一个平移量；\(k\) 不变 ⟹ 比例尺不变 |
| 新旧画布的**公共区域**（交集矩形）里，每个像素看到的地理点都没变 | 6.2 的约束就是在整块交集上成立的 |
| 缩放比例尺不会被 resize 改变 | §4 里 \(BaseScale\) 被冻住 |

| 没证明 / 需要额外说明 | 为什么 |
|---|---|
| **被裁掉的那部分怎么"找回来"** | 推导只保证交集内的像素不变。画布变小后，交集之外的地理区域就是超出视野了——那是用户滚轮 / 拖拽的事，不是 resize 的事 |
| **"居中裁剪"是不是 bug** | 不是。裁剪方向取决于你把哪个 \(s = s_0\) 当定点。我们选了 \(s_0 = 0\)（左上角），所以是"右下方向被裁"。若换成定点在画布中心（\(s_0 = W/2\)），该处 \(x = c_x\)，算出来仍是 \(panDelta = \frac{W - W'}{2}\)——但此时左上是"被裁掉的部分"，所以它会动 |
| **推导本身不约束定点在哪** | \(s_0\) 取任何值，代数都会给出同一个 \(panDelta\)。裁剪方向是我们**外部选**的（本节选了 \(s_0 = 0\)），而且选中的定点在新画布上必须依然可见，否则"钉住"没有意义 |
| **\(k\) 中途被改的情况** | 推导假设 \(k\) 不变。滚轮改的是 \(Zoom\)（\(k\) 里含着它），所以 resize 补偿与缩放事件不能掺在一起做 |

**教训：符号不要凭"对称的感觉"推。**先写下真正要保住的那个量（这里是**地理坐标**），让它等于自身解出未知量；再把具体数字代进去验一遍。特别要警惕"约束写错、代数却给出同一个式子"这种情况——它不会报错，只会让你的断言悄悄失去意义。

### 坑 2：顺手做了一个"多余的参数"

为了支持"从哪边裁剪"，我给 `SetViewport` 加了一个锚点枚举：

```csharp
public void SetViewport(double width, double height, ViewportAnchor anchor = ViewportAnchor.Center)
```

三种锚点（Center / TopLeft / BottomRight）在自检里跑了三遍，全绿。

实际上这我们的式子仅支持将左上角定为锚点：

> "而且实际上你在 SetViewport() 方法没有用过 anchor 变量，在我眼里看来钉住了左上角，不过也不赖，不用改，如果确认这个值没用掉删掉就好。"

方法体从头到尾没读过 `anchor`，三种枚举值算出的是同一个 `panDelta = (旧宽 − 新宽)/2`，三遍自检其实是同一个实现跑了三遍——"三种锚点全绿"是**假象**。

这是很典型的一种坑：**自检跑绿了，但它证明不了它声称证明的东西**。赶紧删掉了枚举、参数和三层循环，免得后来的人以为这里有功能。

**教训：一个参数如果实现的每个分支算出来都一样，那它不是配置，是装饰。**

## 八、可以复用的小结

> [!TIP] 排查"窗口变化引发内容变化"的三步
> 1. **先分清哪些值是"状态"、哪些是"每帧算出来的结果"**。缩放比例、平移量是状态；屏幕坐标是结果。想固定什么，就得固定它的输入。
> 2. **选一个真正的不变量，而不是一个"看起来不该变"的坐标**。本例是 `ToData`（反投影回去的数据坐标），不是屏幕坐标。
> 3. **把"重算比例"从"记录尺寸"里拆出去**。尺寸变化是高频的、被动的；重新 fit 是低频的、用户主动的。两者调用的时机完全不同，混在一个方法里迟早出事。

## 附录：同期修掉的另一个"悬浮窗尺寸"问题

同一天还修了一个 UI 层的相关 bug，一并记下：悬停提示框的位置看起来"范围延伸到正无穷"——鼠标往右下移动时，提示框的可见区域一直铺到画布右下角。

**原因**：提示框是 Grid 的直接子元素，`HorizontalAlignment` / `VerticalAlignment` 默认是 `Stretch`，于是它被拉伸填满整个画布单元格，尺寸根本不由文字决定。再叠一个 `TranslateTransform` 平移 14/18 像素，看到的效果就是"整块画布被涂上提示框底色、整体挪了一点"。

**修法**：改成 `HorizontalAlignment="Left" VerticalAlignment="Top"`，位置用 `Margin` 表达（Stretch 元素里 Margin 等效于左上角坐标），并在贴边时翻到另一侧：

```csharp
HoverTip.UpdateLayout();              // 布局是异步的，刚设完文字时 ActualWidth 还是旧值
var tipWidth  = HoverTip.ActualWidth;
var x = pos.X + gapX;
if (x + tipWidth > canvasWidth)      // 右边放不下
{
    var flipped = pos.X - gapX - tipWidth;
    if (flipped >= 0) x = flipped;   // 左边也放不下就保持原样
}
HoverTip.Margin = new Thickness(x, y, 0, 0);
```

**这里的教训和正文一致**：`Math.Clamp` 夹住别越界是"看起来对"的做法，但它会让提示框压住鼠标；真正符合直觉的行为是**翻面**。放不下就换边，换边也放不下才维持原样。
