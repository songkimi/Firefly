## 太长不看

| 项目 | 内容 |
|---|---|
| **上一集留下的账** | 索引把候选压到 13/8,531，但 8× 单帧还有 46 ms，1× 全幅 807 ms，悬停 402 ms |
| **根因** | 候选之后仍然「把部件的每个点都投影一遍」；悬停则是「每个对象都拿鼠标位置判一遍」 |
| **做法** | ① 先算准**视野框**（`VisibleRect()`：画布四角反解成数据坐标），查询时按它加余量；② 悬停改为只对**屏幕下那几个候选**做几何判定 |
| **两个必须记住的细节** | 余量不是可有可无（线宽、点半径、8 px 命中容差都在框外）；**不能拿顶点判在不在框里**——顶点全在外、边穿过屏幕的形状真实存在（实测 20 处） |
| **数字** | 悬停 402 → **12.7 ms**（中国省界 53.5 → 6.6）；8× 单帧 46 → **24 ms**；1× 807 → **96 ms**（这一笔主要来自后面的合并渲染） |
| **最大的教训** | 「屏幕外的东西不算」这句话，要落到**哪个坐标系、按什么粒度、留多少余量**三个具体决定上，否则会画出缺角的省 |

## 一、索引之后，剩下的钱花在哪

上一篇结束时，索引让"选哪些对象"从 O(n) 变成了一次树查询（0.02 ms）。但 8× 单帧还有 46 ms，1× 更是原地不动——807 ms。

把一帧拆开看就清楚了：

| 一帧在做的事 | 1× | 8× |
|---|---|---|
| 清空上一帧的图元 | 462 ms | 462 ms |
| 找候选（索引） | 0.6 ms | 0.02 ms |
| **把候选的每个点投影 + 换算屏幕坐标 + 造图形** | 392 ms | 43 ms |
| 交给 WPF 光栅化 | — | — |

最后一行当时没有单独量：光栅化发生在渲染线程，探针要到后面才把两个线程分开（第 5 篇）。第 3 行就是"候选之后"的成本：**13 个候选里仍然是 8,531 个点全部投影**（放大之后每个部件反而点更多）。它跟"画多少"成正比，而"画多少"在 8× 下已经很小了——所以真正要砍的是"被否决的对象压根不该走到投影这一步"。

于是问题变成：**怎么在投影之前，就知道"这个部件在不在屏幕上"。**

## 二、视野框：把画布四角反解成数据坐标

`GeoBounds` 手里有三样东西：数据包围盒、缩放、平移。屏幕坐标是它算出来的：

```
screenX = viewportWidth/2  + (x - dataCenterX) * scale * zoom + panX
screenY = viewportHeight/2 - (y - dataCenterY) * scale * zoom + panY
```

那"视野框"就是把这四步反过来：给画布的四角 `(0,0)`、`(W,0)`、`(0,H)`、`(W,H)`，各跑一次 `ToData()`。

```csharp
/// 当前屏幕可见区域，换算回数据坐标（投影后的坐标）。
public (double MinX, double MinY, double MaxX, double MaxY) VisibleRect()
{
    // 注意：屏幕 y 向下、数据 y 向上，所以 (0,0) 是左上角 = (MinX, MaxY)
    var (x0, y0) = bounds.ToData(0, 0);                       // 左上
    var (x1, y1) = bounds.ToData(bounds.ViewportWidth, bounds.ViewportHeight); // 右下
    return (Math.Min(x0, x1), Math.Min(y0, y1),
            Math.Max(x0, x1), Math.Max(y0, y1));
}
```

这段代码只有四行，但它有一个隐蔽的错误可能：**只取两个对角点**。如果 `ToData` 里 x 和 y 的缩放是不一致的（`BaseScale` 与 `zoom` 的乘法顺序、`SpanFloor` 的兜底），两个对角点就够不成矩形，会算出一个歪掉的框。

所以验收里放的是**四条判据**，不是"看起来对"：

| 判据 | 做法 | 结果 |
|---|---|---|
| 对角点回映 | `ToScreen(ToData(0,0))` 必须等于 `(0,0)` | 12/12 通过 |
| 四角各不相同 | 四个角算出的 x 只有两个值、y 只有两个值 | 全部 2/2 |
| 仿射残差 | 在框内网格取 65×65 点，拟合线性关系后测残差 | 4.7e-15 ～ 1.6e-12 |
| 框外单调 | 越出可视区的点，算出来的屏幕坐标必须继续越出 | 12/12 通过 |

最后一项尤其值得写：**这不是"看看数字像不像"，而是一个可证伪的断言**。残差 1e-15 意味着"这条链在数值上就是仿射的";单调性意味着"没有哪一步偷偷把坐标夹回去了"。

## 三、余量：框外的东西不全是垃圾

框算准了，接下来是"往两边各扩多少"。这里有三笔账，一笔都不能省：

| 什么在框外还会画到 | 最大影响 |
|---|---|
| 描边宽度 | 面 5 px、线 6 px → 半个线宽就是 3 px |
| 点的半径 | 缩放最大时 26 px |
| 命中容差 | 悬停判定用 8 px 的容差，鼠标在框边 8 px 内都算命中 |

少了这一圈，效果是**视野边缘的省份会被切掉一角**——不是"偶尔"，是只要边缘有形状就一定发生。这也是它容易被漏掉的原因：眼睛盯着屏幕中间，看不出来。

> [!WARNING] 裁剪最容易犯的错
> 用"数据包围盒 ∩ 视野框"去裁剪，而不是"视野框 外扩余量"。前者会把横跨整个中国的省（比如那个占了六分之一国土的自治区）判成"不在视野里"，因为它的包围盒中心在图外。

## 四、悬停：从"每个对象都判"到"只判屏幕下那几个"

悬停的老路径是这样的：

```csharp
// 改之前：每次鼠标动，把整个图层跑一遍
foreach (var feature in _layer.Features)
    if (HitTest(feature, 鼠标位置, 容差 8)) return feature;
```

`GeoLayer` 有 4,595 个对象、129 万个点。鼠标每动一次、每 40 ms 定时器滴答一次，都要跑一遍——**402 ms**。日志里"移动鼠标就卡"的体感，主要就是它。

改法不是"把循环写快一点"，而是**换掉遍历的集合**：既然已经有索引，就先问"光标 8 px 内有哪些候选"，再只对这些候选做几何判定。

```csharp
// 改之后：先查树，再判几何
var hits = QueryCandidates();          // 屏幕内的候选（13 个量级）
foreach (var hit in hits)              // 只对这十几个做精确判定
    if (HitTest(hit.Points, 鼠标位置, 8)) return hit.Feature;
```

顺序也要对：**先把索引查出来，再判命中**。反过来的话，还是得为每个对象算一遍"它在不在屏幕里"。

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 悬停（ne_10m，8,531 部件） | 402.4 ± 9.1 ms | **12.7 ± 4.9 ms** |
| 悬停（中国省界，1,313 部件） | 53.5 ± 2.7 ms | **6.6 ms** |

顺带一个容易忽略的点：**候选取自屏幕范围，但命中容差是 8 px**。所以查询矩形要按容差外扩，否则"鼠标在省份边缘外侧一点点"就判不中了——用户会觉得"这个省点不到"。

## 五、"顶点全在框外、边穿过屏幕"的那 20 处

做剔除时，最自然的写法是"逐点判断在不在框里"：

```csharp
// 看起来对，实际会漏
if (screenX < 0 || screenX > width || screenY < 0 || screenY > height) continue;
```

它有一个真实的漏洞：**一条从屏幕左侧外连到右侧外的线，两个端点都在框外，但它的中间段横穿整个屏幕。** 一个占满视野的省，完全可能所有顶点都在视野外（比如 20× 放大到某个省内部），逐点判定会把它整个丢掉——屏幕上本该是实心的绿，变成空的。

这也是为什么我最后把"逐点筛选"整个删掉：**判断"在不在视野里"这件事，包围盒说了算，而不是顶点**。包围盒相交就画，让 `Canvas` 的 `ClipToBounds` 去负责"多画的部分不显示"。

删掉逐点筛选之后，像素对照第一次不再全绿：

| 指标 | 结果 |
|---|---|
| 画布内差异 | **20 处**（是**多出来的**，不是少画的） |
| 多出来的是什么 | 顶点全在画布外、但边真的穿过画布的对象 |

也就是说：包围盒给出的"多给"并不全是浪费，其中一部分正是原来的判定漏掉的。

## 六、数字

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 悬停（ne_10m） | 402 ms | **12.7 ms**（32×） |
| 悬停（中国省界） | 53.5 ms | **6.6 ms**（8×） |
| 8× 单帧（ne_10m） | 46 ms | **24 ms** |
| 1× 单帧（ne_10m） | 807 ms | **96 ms** |
| 视野框验算 | — | 12/12 通过，残差 ≤1.6e-12 |

1× 那一行的大头其实不是剔除，是后面几篇里"把 8,531 个图元合成 1 个"那件事。但有一点值得先记住：**全幅时剔除一无所得**——所有对象都在视野里，候选就是全部。剔除解决的是"放大之后还带全量"的问题。

## 七、可以复用的小结

> [!TIP] 视口裁剪的五步
> 1. **先算视野框，并证明它是对的**：对角回映、四角取值、仿射残差、框外单调。这四条比"看起来对"结实得多。
> 2. **外扩余量按"最大视觉影响"算**：线宽的一半、点半径、命中容差，取最大值。
> 3. **用包围盒判在不在视野里，不要用顶点**。顶点全在外、边穿过屏幕的形状是真实存在的。
> 4. **悬停这类"每像素触发"的操作，要换遍历集合**，不是把循环写快。
> 5. **查询矩形记得按命中容差外扩**，否则边缘对象会"点不到"。
