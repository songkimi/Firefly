## 太长不看

| 项目 | 内容 |
|---|---|
| **目的** | 优化之前先有尺子。三套数据 × 三个数字（打开 / 一次重绘 / 一次悬停），作为后面所有改动的"改之前" |
| **为什么 `Stopwatch` 不够** | 它量的是"我的代码跑了多久"。用户却只管看到"我动了鼠标，画面什么时候变"——中间还有排队和渲染两段，`Stopwatch` 一段都看不见 |
| **探针** | 一个独立小程序：`CompositionTarget.Rendering` 当帧时钟，`e.Timestamp` 当"输入进来的那一刻"，于是排队 / UI 线程 / 到上屏三段都能量 |
| **量到的** | 拖动一帧 UI **429 ms** + 渲染 **738 ms** = **1,167 ms**；连拖 10 次的事件积压到 **9.3 秒**，最后一帧 **10.2 秒**才上屏 |
| **基线（改之前）** | ne_10m：打开 3,764 / 重绘 807 / 悬停 309 / 8× 重绘 349 ms。中国省界：548 / 55.5 / 48.2 / 50.4 |
| **尺子错了五次** | 顺序效应、对照物不等价、少算了一笔清空、P90 没排序、探针自己的覆盖层污染测量点 |
| **最大的教训** | 一个数字只有在**别人能复现、且对着同一条路径**时才算证据。改了代码之后数字变好，也可能只是尺子松了 |

## 一、要量的到底是什么

项目是一个 WPF 的 GeoJSON / Shapefile 查看器。数据从几百个点到一百多万点不等，画布 1,105 × 674。

"移动缩放响应大约 5 秒才刷新"。这句话里藏着两个不同的量：

1. **一帧要多久**（一次重绘的成本）；
2. **从"我动了"到"我看见"要多久**（包含排队）。

尺子开始只量了第 1 个。第 2 个才是体感，而它比第 1 个大得多——大到你优化完第 1 个，实际用起来还是很卡

所以尺子要能回答三件事：

| 问题 | 对应字段 |
|---|---|
| 这个事件在 Windows 队列里等了多久才进我的回调？ | 排队 |
| 我的回调（UI 线程）占了多久？ | UI |
| 我从回调里退出到"这一帧真的上屏"，又等了多久？ | 到上屏 |

## 二、第一把尺子：`Stopwatch` 打点

最自然的写法：

```csharp
private void OnMouseMove(object sender, MouseEventArgs e)
{
    if (!_dragging) return;
    var sw = Stopwatch.StartNew();
    RebuildView();              // 清空 + 重建 8,531 个图元
    _lastMouseMoveCost = sw.Elapsed.TotalMilliseconds;
}
```

量出来 400 毫秒左右。合理，但解释不了"5 秒"。

原因是它只覆盖了中间那一段：

```
[输入事件进入队列] ──排队──▶ [回调执行] ──UI──▶ [返回]
                                              │
                             ┌────────────────┷────────────────┐
                             │  WPF 渲染线程：光栅化 + 合成 + 上屏 │
                             └────────────────┬────────────────┘
                                              ▼
                                         [用户看见]
```

WPF 的 UI 线程和渲染线程是分开的。你在 UI 线程上花 400 ms，渲染线程还要再花几百毫秒把这些图元光栅化成像素。而"排队"这一段，只有当下事件的时间戳能告诉你。

**教训：`Stopwatch` 量的仅是"线程花费"，不是"实际体验"。**

## 三、探针：用帧时钟当天平

WPF 有一个事件天生是"帧的节拍"：

```csharp
CompositionTarget.Rendering += OnRendering;   // 每次合成一帧之前触发
```

于是探针的三个数据源就齐了：

1. **帧时钟**：每次 `Rendering` 回调就是一个帧的边界。
2. **输入时刻**：`MouseEventArgs.Timestamp` 是消息进入队列时的 tick。`Environment.TickCount64 - e.Timestamp` 就是它在队列里等了多久。
3. **上屏时刻**：回调返回之后，等到**下一次** `Rendering` —— 那一刻这一帧已经提交给合成器了。

把它抽成一条记录：

```csharp
private sealed class Record
{
    public string Kind = "";      // 平移 / 滚轮 / 悬停
    public double QueueMs;        // 排队：事件进来时算好
    public double UiMs;           // UI 线程耗时
    public double ToScreenMs;     // 到上屏：UI 返回 → 下一次 Rendering
    public double TotalMs;        // 端到端
}
```

探针是**独立程序**，不是给主程序加日志：它自己开一个真窗口、真的加载数据、真的模拟输入，然后把表打出来。这样做的好处是它永远量同一件事，不会因为主程序改动而失准（代价是它得跟着架构改——见第五节第 5 条）。

跑出来的表长这样（1× 全幅，8,531 个部件）：

| 阶段 | 中位 | 最大 |
|---|---|---|
| 排队（事件在队列里等） | 31 ms | 4,235 ms |
| UI 线程 | 429 ms | 466 ms |
| 到上屏（渲染线程） | 738 ms | 2,024 ms |
| **端到端** | **1,167 ms** | — |

这里有个立刻能看出来的事实：**UI 线程和渲染线程差不多一样贵**。所以"优化 UI 线程"最多只能把 1,167 砍到 738。

还有一张更好看的表：连发 10 次平移事件，看第 1 帧什么时候上屏。

| 尝试 | 事件积压总时长 | 第 1 帧真正上屏 |
|---|---|---|
| 第 1 次 | 9,060 ms | 10,243 ms |
| 第 2 次 | 9,369 ms | 10,462 ms |

10 次移动 = 10 秒。这就是"5 秒"的来源：每个 `MouseMove` 都排一个全量重画，而队列里的事件一个都不会被丢掉。

## 四、基线：三套数据 × 三个数字

优化要有"改之前"，所以先用同一把尺子量三套规模差三个数量级的数据（每项预热 2 次、量 9 次取中位）：

| 数据集 | 对象 / 部件 / 点 | 打开合计 | 一次重绘（1×） | 一次悬停 | 一次重绘（8×） |
|---|---|---|---|---|---|
| ne_10m 省级 | 4,595 / 8,531 / 1,290,065 | 3,764 ms | 807 ms | 309 ms | 349 ms |
| 中国省界 | 1,313 / 1,313 / 164,021 | 548 ms | 55.5 ms | 48.2 ms | 50.4 ms |
| 贵州省 | 19 / 19 / 5,590 | 18.2 ms | 1.5 ms | 1.4 ms | 1.2 ms |

读这张表要注意两件事：

- **小数据已经很快了**（1.5 ms），优化它没有意义。所以后面所有结论都以 ne_10m 为准，另外两套只用来确认"没有把快的搞慢"。
- **8× 比 1× 只快一半多**（349 vs 807）。按"画得少就该快"的直觉，8× 应该快一个数量级才对。这个反常是后面空间索引那篇的入口。

## 五、尺子自己错了五次

这一节比前面的表都重要。同一个项目里，我先后把尺子弄错五次，每次都让"优化有效"变成一句假话。

### 5.1 顺序效应：先跑的那个永远更慢

第一版对照表里，旧路径**先**测，新路径**后**测。结果旧路径总慢一截。原因很朴素：第一次跑要付 JIT、要付第一次分配的开销。

验证方式很土：把旧路径挪到最后再测一次。

| 旧路径的测量位置 | 中位 |
|---|---|
| 先测 | 320 ms |
| 最后测 | 220 ms |

同一段代码，同一个数据，差 100 ms。**所以对照表里"旧路径"必须最后量，且要留一行"顺序效应"记录，否则读者没法判断差值里有多少是顺序。**

### 5.2 对照物不等价

第二轮，"改之前"画的是**未做基准转换**的图层（8,531 个部件），"改之后"画的是转换后拍平的图层（4,595 个部件）。

于是"改之后更快"里，有一半是"画的少"换来的，跟优化无关。

**教训：对照的两边必须是同一条数据路径的两个实现，不是两个不同的输入。**

### 5.3 少算了一笔清空

"改之前"直接调渲染器往一张一次性画布上画，"改之后"走的是窗口那条路（每帧先 `Children.Clear()`）。

而清空 8,531 个 `UIElement` 要 **462 ms**——比画（392 ms）还贵。这笔钱"改之前"根本没付。

修正之后两边都含清空，差距立刻缩水一大截 —— 于是我把"清空"单独列成一行（462 ms），而不是让它藏在某一侧的耗时里。**不是代码变了，是账算全了。**

### 5.4 P90 比中位还小

探针日志里有一行"帧间隔 P90"，长期小于中位。当时以为是数据抖动，后来发现是排序：

```csharp
// 错的：文档要求 sorted，但调用方按时间顺序传进来的
private static double Percentile(List<double> sorted, double p) => sorted[(int)(sorted.Count * p)];
```

改成内部 `OrderBy` 之后，同一次压测里中位 26 ms、P90 363 ms —— 这才像个分位数。**一个自己都不知道自己在算什么的分位数，比没有更危险。**

### 5.5 探针的监控点被自己污染

探针在窗口上叠了一个小覆盖层，实时显示当前耗时。它每收到一个事件就更新一次文字——布局 + 文本渲染都在 UI 线程上。

于是"1× 拖动帧间隔 P90 33.5 ms"这个数，有一大半是探针自己造成的。换一个不带覆盖层的压测工具量同一个场景：P90 **12.1 ms**。

**教训：测量工具本身要在被测量的路径上"几乎不花钱"。做不到就分两个工具：一个负责看（带覆盖层），一个负责量（什么都不显示）。**

## 六、怎么读探针日志

日志一段一段的，按这个顺序看：

1. **先看"有重建的帧"**。没有重建的帧只反映鼠标移动，不代表任何绘图成本（尤其是在"拖动不重画"之后，几乎所有帧都落在这一类）。
2. **再看"排队"**。排队中位高 = 上一帧太贵，事件在等；排队中位接近 0 而端到端还是高 = 钱花在当前这一帧。
3. **最后看"端到端 P90 与最大"**。中位好看不代表手感好，卡顿是长尾现象。

## 七、可以复用的小结

> [!TIP] 做 UI 延迟测量的五条
> 1. **先定义"用户感知的量"**：是"事件到上屏"，不是"函数耗时"。两者可能差一个数量级。
> 2. **用帧时钟当边界**：`CompositionTarget.Rendering` 是 WPF 里唯一诚实的"这一帧结束了"的信号。
> 3. **把等待拆成排队 / 计算 / 渲染三段**，否则你永远不知道该改哪一段。
> 4. **对照实验里，顺序、数据、路径三者必须对齐**，并把"顺序效应"单独列出来。
> 5. **测量工具自己也要被测量**：它在 UI 线程上多画一个覆盖层，就可能把你正在量的东西放大三倍。

下一篇从这个"8× 只快一半"的怪现象讲起：为什么画的东西少了十倍，时间却只少一半。
