## 太长不看

| 项目 | 内容 |
|---|---|
| **反常现象** | 1× 全幅一帧 **807 ms**，可画的东西并不算多（8,531 个部件）；拆开一看 **462 ms 花在"清空上一帧"** |
| **根因** | 每个部件一个 `Shape`（`Polygon`/`Polyline`/`Ellipse`）。`Children.Clear()` 要拆 8,531 个 `UIElement`，然后再造 8,531 个，每个都要走测量/排列/资源注册 |
| **做法** | 一个 `DrawingVisual` + 一次 `RenderOpen()`，循环里只调 `DrawGeometry`；笔提到循环外复用（本层只有点/线/面三套样式） |
| **最坑的一次尝试** | 把所有面塞进**一条** `StreamGeometry`：构建 7.8 秒——几何本身成了瓶颈 |
| **数字** | 1× 重绘 807 → **96.6 ms**；8× 46 → **24 ms**；拖动/缩放中的"粗版"让滚轮 1.4 s → **173 ms** |
| **最大的教训** | WPF 的"元素"是有成本的：**数量**比"画得多复杂"更贵。能把 N 个元素变成 1 个，就先做这件事 |

## 一、"清空"是这一帧里最贵的一笔

这个数在第 4 篇已经拆过一次（1× 全幅：清空 462 ms / 找候选 0.6 ms / 画 392 ms），这里只补一句**它为什么会发生**：

`MapCanvas.Children` 里躺着 8,531 个 `UIElement`。每一个都有自己的属性系统、视觉树节点、布局状态。清空不是"把一块画布擦干净"，是**把 8,531 个对象从三棵树里摘下来**。

而"擦干净再画新的"这个模式，本身就是这个结构的产物：`Shape` 是不可变的图形元素，坐标变了只能重建。

---

## 二、第一个想法是错的

最直觉的改法是：既然 WPF 嫌元素多，那就**只用一个几何**——把 8,531 个面合并成一条 `StreamGeometry`，一次 `DrawGeometry` 画完。

写出来，跑一下：**7.8 秒**。比原来还慢 8 倍。

为什么？因为 `StreamGeometry` 的 `BeginFigure`/`LineTo` 在构建期要做包围盒、简化、路径段合并这些事。8,531 个部件、129 万个点，全部塞进同一个几何，构建成本直接从"画"的范畴跳到了"预处理一整张图"。

> [!WARNING] "合并成一个"要合到哪一层
> 合并的正确层次是**绘制指令**，不是**几何数据**。`DrawingVisual` 里可以有 8,531 次 `DrawGeometry`，这和"8,531 个 `Shape`"性质完全不同——前者是"一个元素里的 8,531 条绘制记录"，后者是"8,531 个元素"。

## 三、正解：一个 visual，多条小几何

```csharp
var visual = new DrawingVisual();
using (var dc = visual.RenderOpen())
{
    // 笔在循环外：本层只有点/线/面三套样式，尺寸只跟缩放有关
    var penLine = new Pen(brushLine, lineWidth);
    var penArea = new Pen(brushAreaEdge, areaWidth);
    var brushArea = new SolidColorBrush(...);

    foreach (var feature in features)
        foreach (var part in feature.Geometry.PartsOrSelf())
        {
            var geometry = BuildGeometry(part);      // 每部件一条小几何
            if (geometry is null) continue;

            if (kind is Area)
            {
                dc.DrawGeometry(brushArea, penArea, geometry);   // 先填充
                dc.DrawGeometry(null, penArea, geometry);        // 再描边
            }
            else
            {
                dc.DrawGeometry(null, penLine, geometry);
            }
        }
}
```

三个决定：

1. **每个部件一条几何**，不做跨部件合并（避开上一节那 7.8 秒）。
2. **笔在循环外**。`Pen` 是不可变对象，`DrawGeometry` 只是引用它；每画一次 new 一支笔，是白送给 GC 的垃圾。
3. **填充和描边交给同一次 `DrawGeometry`**。`DrawGeometry(brush, pen, geometry)` 一次就把两件事都交代了；渲染线程内部仍然会展开成"填充 + 描边"两笔工作，但对我们来说只有一条命令、一套几何，不必像 `Shape` 那样靠两个元素去拼。

结果：

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 1× 单帧 | 807 ms | **96.6 ms**（8.4×） |
| 8× 单帧 | 46 ms | **24 ms** |
| 一帧里的"清空" | 462 ms | **0**（只清理一个 visual 的绘制记录） |

这 700 多毫秒省在哪，得说清楚，否则很容易被读成"合并把光栅化变快了"——**没有**。投影还是一条不少地跑，8,531 条描边也一条不少地画。省掉的是两笔"包装"成本：一是清空那 462 ms；二是 8,531 个 `Shape` 各自作为子元素被创建、挂图、参与布局与合成的开销（"画"从 392 ms 掉到 92 ms，而 92 ms 基本就是那 129 万个点的投影本身）。

## 四、像素变了吗

换了绘制方式，第一个要回答的是"画出来还一样吗"。像素对照：

| 指标 | 结果 |
|---|---|
| 差异像素 | 39,170（约 5.3%） |
| 差异位置 | 全部落在**描边上**（共享边、折角） |
| 最大通道差 | 66 |
| 结构性差异 | 0 |

原因不神秘：以前 8,531 个 `Shape` 各自是独立的光栅化单元，相邻省份共享的那条边界由两个元素各画一次，抗锯齿的覆盖在各自单元里算；合并之后这两笔仍画两次、顺序也照旧，但它们在同一个绘制通道里，子像素覆盖的舍入不同，于是边缘几个像素的亮度差一点点。

这就是"逐像素不变"这类验收在新方案下**注定失败**——不是画错了，是叠色规则变了。所以判据必须换：**看结构，不看像素**（有没有少形状/少省份、最大的差异有多大、差异是不是都在边缘）。

## 五、粗版：先画能看的，再补对的

合并之后，最贵的剩下"投影 129 万点 + 造几何"。拖动时每帧都要付，缩放时更是——滚轮一格 1.4 秒。

这里用了一个老办法：**交互期间画粗的**。

先量清楚"粗的"能省多少（1.5×，8,531 个部件）：

| 版本 | 建几何（UI 线程） | 光栅化（渲染线程） | 合计 |
|---|---|---|---|
| 细版（1 px 抽稀 + 描边） | 113 ms | 900 ms | 1,014 ms |
| 4 px 抽稀 + 描边 | 108 ms | 885 ms | 992 ms |
| 4 px 抽稀 + **不描边** | 98 ms | 119 ms | **217 ms** |
| 8 px 抽稀 + 不描边 | 100 ms | 113 ms | 213 ms |

两条反直觉的结论：

1. **省的是描边，不是顶点。** 去掉 8,531 条抗锯齿描边，光栅化 900 → 119 ms（平均每条 92 µs）；而 4 px 和 8 px 抽稀几乎一样快——顶点数在光栅化里几乎不值钱。所以这笔账不是按"部件个数"付的，也不是按"顶点点数"付的，是按**要光栅化的绘制记录条数**付的：填充那条本来就有，多出来的 8,531 条描边才是大头。我们一开始把 1.4 秒归因于"顶点太多"，方向错了。
2. **建几何只要 100 ms。** 129 万个点的投影全在这 100 ms 里，剩下 900 ms 全是光栅化。所以任何"CPU 侧少算点东西"的优化，天花板就是这 100 ms——真正的钱在渲染线程。

落地：

| 状态 | 画法 |
|---|---|
| 拖动中 / 滚轮刚结束 | 抽稀到 4 px 容差、**不画描边**、点和线也合并成几何 |
| 停手 250 ms 后 | 排一次"补细"，用完整精度重画 |

```csharp
var coarse = _dragging || _coarsePending;
if (coarse) RenderCoarse(parts, settings, bounds, canvas, tolerancePx: 4.0, drawStrokes: false);
else        Render(parts, settings, bounds, canvas);

// 缩放那一帧是粗的：紧接着排一次"空闲补细"
if (coarse && !_dragging) ScheduleFineUpgrade();
```

两个坑：

1. **补细的那一帧不能又画成粗的**：定时器回调里先把 `_coarsePending` 清掉，再请求重画，否则死循环（每帧都"粗"、永远不"细"）。
2. **松手不能无条件重画**：粗版落地时排 250 ms 的空闲补细；如果这 250 ms 内用户又动了，取消它。

效果：

| 操作 | 改之前 | 改之后 |
|---|---|---|
| 滚轮一格（×1.5） | 1.4 s | **173 ms**（粗版到屏），151 ms 后补细 |
| 拖动中每帧 | 与缩放同价 | 6 ms（只挪位图，见上一篇） |

粗版看起来会"糊"一下——没有描边、边缘少几个点。这在交互期是可接受的：**用户要的是"它跟手"，不是"它此刻精确"**。

---

## 六、预抽稀（LOD）：把"少画点"变成缓存

粗版每次都要现场抽稀 129 万点，几百毫秒。所以加了一层缓存：按"屏幕容差"分档（0.5 / 1 / 2 / 4 / 8 px），同一档的结果缓存起来，下次直接取。

| 缩放 | 抽稀后点数 | 效果 |
|---|---|---|
| 1× | 几乎不变（点本来就挤在一起） | 无收益 |
| 1.5×–2× | 明显减少 | 明显 |
| 8× | 只剩视野内的部件 | 24 ms |

**代价必须说清楚**：抽稀之后画面和"全精度"不再逐像素相同（实测 6% 左右的像素不同，全部在边缘）。它是"可接受的不精确"，不是 bug——所以在产品里，抽稀只在交互期间用，落定后一律补全精度。

## 八、可以复用的小结

> [!TIP] 把 N 个元素合成 1 个的四条
> 1. **先看数量**：`Children.Clear()` 的耗时和元素数成正比，和图形复杂度无关。几千个以上就该考虑合成。
> 2. **合并"绘制记录"，不要合并"几何数据"**。一个 `DrawingVisual` 里可以画 8,531 次；把所有形状塞进一条 `StreamGeometry` 反而更慢。
> 3. **笔/刷提到循环外**。它们不可变、可复用，每帧 new 一遍只是制造 GC。
> 4. **判据从"逐像素相同"换成"结构相同"**：叠色规则变了，像素必然变；要盯的是有没有少东西、最大差异多大、差异在不在边缘。

到这里，单帧成本这条线走完了：807 → 96 ms（全幅）、349 → 46 → 24 ms（8×，一半是索引、一半是合并）。剩下的是"打开文件"那 3.6 秒——它花在读文件、建索引和第一次画上，属于另一类问题。
