## 太长不看

| 项目 | 内容 |
|---|---|
| **反常现象** | 单帧 1,167 ms，但"拖一下"要等 5 秒。连续移动 10 次，界面愣住 **9.3 秒** |
| **根因** | 每个 `MouseMove` 都**同步**跑一次完整重画。一次重画 1.1 秒，而鼠标一秒能发 60 次事件——队列越积越长，你看到的永远是 5 秒前的画面 |
| **做法** | 帧调度：事件里只置一个"待重画"标记，真正的绘制统一挂在 `CompositionTarget.Rendering` 上（渲染帧回调），**一帧最多画一次** |
| **怎么量** | `Environment.TickCount64 - e.Timestamp` = 这个事件在队列里排了多久；再加"绘制耗时"和"到屏幕"，就是三段 |
| **数字** | 积压 10 次移动：9,060 ms → **一帧**；拖动会话 5,670 ms → 长会话里只重画 2–3 次 |
| **最大的教训** | "慢"有两个来源：**一帧多贵** 和 **一秒画几帧**。只优化前者，后者会让所有努力白费 |

## 一、5 秒不是画出来的

先看一组真实日志（探针跑出来的，每次拖动记一行）：

| 场景 | 从按下到画面变化 |
|---|---|
| 平移 1 次 | 1,167 ms |
| 平移 8 次（连续） | 8,000 ~ 9,300 ms |
| 平移 20 次（连续） | 超过 20 秒 |

单次 1.1 秒，8 次应该 9 秒左右——数字对得上，但对不上的地方在别处：**用户只拖了 0.2 秒，为什么画面卡了 8 秒？**

因为事件不是"一次一个"来的。鼠标移动时 `MouseMove` 每秒能发几十次，而每一次都触发了一次完整重画：

```csharp
// 改之前：每次鼠标移动都同步重画
private void OnCanvasMouseMove(object sender, MouseEventArgs e)
{
    if (!_dragging) { ... }
    _bounds.PanX += dx;
    _bounds.PanY += dy;
    RebuildView();          // 1,167 ms，在 UI 线程上同步跑
}
```

第一个事件花 1.1 秒画完，后面 60 个事件已经在队列里排队了。画完一个，下一个立刻开始——**队列永远追不上鼠标**。这就是"拖动像幻灯片"的真相：不是画得慢，是**画得太多次**。

## 二、把一帧拆成三段

要证明上面这个说法，得能分别量出三段时间。WPF 的 `MouseEventArgs.Timestamp` 是从系统启动起的毫秒数（和 `Environment.TickCount64` 同一个时钟），于是：

```csharp
// 事件到达（我们终于拿到它）时，它已经在队列里等了多久
long queueMs = Environment.TickCount64 - e.Timestamp;

// 我们处理它 + 画完，花了多久（UI 线程）
var sw = Stopwatch.StartNew();
... // 重画
long uiMs = sw.ElapsedMilliseconds;

// 从画完到屏幕上真的变了（用 CompositionTarget.Rendering 等下一帧）
long toScreenMs = ...;
```

三段的意义完全不同：

| 分段 | 高说明什么 | 该改哪里 |
|---|---|---|
| 排队（queue） | 事件积压 | 少画几次（调度） |
| UI（ui） | 一帧太贵 | 少画东西（索引/裁剪/合并） |
| 到屏（toScreen） | 光栅化/合成太贵 | 换画法（DrawingVisual/位图） |

改之前的三段是 排队 31/110/4,235 ms（中位/P90/最大）、UI 429 ms、到屏 738 ms。**排队的最大值 4.2 秒**——这就是"拖一下等 5 秒"的出处。

> [!TIP] 一个值得注意的细节
> 排队时间是**负不了**的，但也**不总是真实**的：如果事件是程序自己合成的（比如测试工具 `RaiseEvent`），`e.Timestamp` 会是我们生成它的时刻，排队就恒为 0。做探针时要记得区分"真实输入"和"合成输入"。

## 三、一帧只画一次

改法很小：事件里只记账，画的时候统一在渲染回调里画。

```csharp
private bool _redrawPending;

/// 任何需要重画的地方都调这个，不直接画
private void RequestRedraw()
{
    if (_redrawPending) return;          // 已经排上了，不重复排
    _redrawPending = true;
}

/// 每帧回调（渲染线程节奏，约 60 Hz）
private void OnFrameTick(object? sender, EventArgs e)
{
    if (!_redrawPending) return;
    _redrawPending = false;
    RebuildView();                        // 一帧最多画一次
}
```

构造函数里挂上：`CompositionTarget.Rendering += OnFrameTick;`

`MouseMove` 变成：

```csharp
_bounds.PanX += dx;
_bounds.PanY += dy;
RequestRedraw();        // 0.001 ms，立刻返回
```

效果：

| 场景 | 改之前 | 改之后 |
|---|---|---|
| 积压 10 次移动 | 9,060 ms | **一帧**（~18 ms 后画面就在动） |
| 拖动会话（长） | 5,670 ms | 只重画 2–3 次 |
| 松开鼠标到画面定稿 | — | 42–449 ms |

最后一行要说明：**最后一次移动必须被画出来**。帧回调每帧只消费一个"待重画"标记，如果用户松开手时还有一次没画，必须保证它最终还是画了——否则画面会停在半路。所以 `_redrawPending` 不能在 `RebuildView` 里被清掉又不再触发，顺序是"先清标记、再画"，画的过程中新来的请求会重新置位。

## 四、验证：用"积压"这个指标

帧调度最怕的是"看着流畅了，其实漏画了最后一帧"。所以验收不看感觉，看两个可测的东西：

| 判据 | 做法 | 结果 |
|---|---|---|
| 积压消失 | 合成 10 次连续 `MouseMove`，量从第一次到画面变化的时间 | 9,060 → **一帧** |
| 不丢最后一帧 | 拖动结束后等 500 ms，比对"最后位置"与"鼠标位置" | 一致 |
| 每帧最多画一次 | 数一帧内 `RebuildView` 被调用次数 | 1 |

第二条尤其重要。`RequestRedraw` 是"合并"语义，合并的代价就是**可能合并掉最后一次**——如果事件在渲染回调之后立刻到来，它要等到下一帧，这没问题；但如果程序在退出/失焦时不画了，就会停在旧画面。

---

## 五、三件容易做错的事

1. **别在事件里 `InvalidateVisual()`**：那只是把重画排到布局之后，仍然按事件次数排；`CompositionTarget.Rendering` 才是"每帧一次"的锚点。
2. **别用 `DispatcherTimer` 做帧源**：15 ms 的定时器不是和屏幕刷新对齐的，会抖。渲染回调天然跟着 vsync。
3. **别在帧回调里做重活之外的事**（弹窗、写文件、查库）——它跑在 UI 线程，一卡就是整帧卡。

## 六、数字

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 积压 10 次移动 | 9,060 ms | 一帧 |
| 排队时间最大值 | 4,235 ms | 0 |
| 单帧本身 | 1,167 ms | 1,167 ms（**这一篇没让它变快**） |
| 拖动体验 | 5 秒级 | 跟手（但重算时仍会跳） |

最后一行是关键：**帧调度只改变"何时画"，不改变"画多贵"**。所以它必须和后面那几篇（裁剪、合并、位图）一起用；单用它，你会得到"很跟手的卡"——每帧还是一秒，只是不再排队了。

## 七、可以复用的小结

> [!TIP] 做帧调度的五步
> 1. **先量三段**：排队 / UI / 到屏。只量总时间，你永远不知道该改哪里。
> 2. **事件里只记账**，绘制统一挂 `CompositionTarget.Rendering`，用布尔标记合并同帧请求。
> 3. **保证最后一帧被画**：合并语义要配一个"结束时强制画一次"的兜底。
> 4. **验收用积压指标**，不要用"感觉流畅"。
> 5. **记住它不降低成本**：它是把"慢但排队"变成"慢但不排队"，真正省时间的是下一层。

下一篇把这条线接到拖动上：既然"重画一次"这么贵，那就不画——只挪一个变换或一张位图。从 1,167 ms 到 6 ms，靠的是三个决定：图元复用、位图缓存、多画一屏。
