## 太长不看

| 项目 | 内容 |
|---|---|
| **反常现象** | 8× 放大后视野里只剩 77 个部件（全图 8,531 个），一帧 349 ms；1× 全幅 807 ms。**画的少十倍，时间只少一半** |
| **根因** | 没有空间索引。每帧把 1,290,065 个点全部投影一遍，再逐个判定，"画不画"是在**最贵的那一步之后**才决定的 |
| **做法** | 抽一个 `IFeatureFinder` 接口，先写**参照实现** `LinearFinder`，再写 `StrtreeFinder`（NetTopologySuite 的 `STRtree`），两者对同一输入必须给出同一批候选 |
| **三个决定成败的细节** | ① 包围盒按**部件**而不是对象建；② 索引里存的是**投影坐标**，而回传的几何是**经纬度**；③ 索引必须跟着图层和投影重建，失效点要穷举 |
| **数字** | 建索引 174 ms；一次查询 **0.02 ms**；候选 **13 / 8,531**（0.2%）；8× 单帧 **349 → 46 ms**（索引，7.5×）；再合并渲染后到 24 ms |
| **最大的教训** | "快"不是目标，"和慢的那个答案一样"才是。参照实现存在的意义就是让你能证明新实现**没漏**，而不只是"快了很多" |

## 一、起点：一个不合逻辑的数

前一篇的基线表里有这么一行：

| 场景 | 一帧耗时 |
|---|---|
| 1×（全部 8,531 个部件都在视野里） | 807 ms |
| 8×（只有 77 个部件在视野里） | 349 ms |

画的东西少了 **110 倍**，时间只少了 **2.3 倍**。如果成本真的跟着"画多少"走，8× 应该快到几十毫秒。

这个比例说明：**一帧里有一大块成本跟视野无关**。顺着查下去，它藏在"决定画哪些"这一步：

```csharp
// 改之前：每个图元都先算，再判断在不在视野里
foreach (var feature in _layer.Features)
    foreach (var part in feature.Geometry.PartsOrSelf())
        foreach (var point in part)
        {
            var (x, y) = Projection.Project(point, _settings);   // 129 万次
            var (sx, sy) = _bounds.ToScreen(x, y);
            if (sx < -50 || sx > width + 50) continue;           // 到这里才知道要不要画
            // ... 加进图元
        }
```

**判定发生在投影之后。** 所以无论放大多少倍，1.29M 个点都得先投影一遍。这就是那 300 多毫秒。

正确的顺序应该反过来：**先确定"这一帧要用哪些对象"，再只给它们投影。**

## 二、先写一个慢的

在写索引之前，先写了一个"故意笨"的实现。它的唯一职责是**给出正确答案**。

接口只要一个方法：

```csharp
/// <summary>
/// 给一个数据矩形，返回与它包围盒相交的所有"部件"。
/// 契约：不能少给（少了画面上就缺东西）；可以多给（多了只是白画）。
/// </summary>
public interface IFeatureFinder
{
    IReadOnlyList<GeoPartHit> Query(
        GeoLayer layer, ProjectionSettings settings, GeoRect rect, double padX, double padY);
}
```

参照实现 `LinearFinder` 的全部逻辑就是一句：遍历所有部件，把它的投影包围盒算出来，与查询矩形相交就收。

```csharp
foreach (var feature in layer.Features)
    foreach (var part in feature.Geometry.PartsOrSelf())
    {
        if (!BoxOf(part, settings).Intersects(rect)) continue;   // 每个部件都投影一遍
        result.Add(new GeoPartHit(feature, part));
    }
```

它慢得和改之前一样（1.29M 次投影），但有三件事：

1. **它是"改之前"那条路径的精确复刻**，所以可以作为"改之后"的裁判；
2. **它没有状态**，不会被"上一次查询"影响；
3. 写它只花 20 行，而它让后面每一个优化都能被**证明**而不是被"感觉"。

> [!TIP] 参照实现三问
> 写之前先回答：它比目标实现慢多少？（这里 100 倍，可以接受）它能不能被随机化对拍？（能，同一个矩形两边比）它会不会和主实现共享状态？（不会，它无状态）

## 三、再写快的：STRtree

`NetTopologySuite` 自带 `STRtree<T>`：批量插入一批"带包络的对象"，然后按包络查询。它不是精确几何索引——**它给的是"包络相交"的候选集**，这正好符合契约里"可以多给"。

插入的东西决定了粒度：

```csharp
var tree = new STRtree<GeoFeature>();
foreach (var feature in layer.Features)
{
    var envelope = new Envelope(minX, maxX, minY, maxY);   // 投影坐标
    tree.Insert(envelope, feature);
}
tree.Build();   // 一次性建树
```

查询时给一个矩形：

```csharp
var envelope = new Envelope(rect.MinX - padX, rect.MaxX + padX, rect.MinY - padY, rect.MaxY + padY);
var hits = tree.Query(envelope);   // IList<GeoFeature>
```

三个数字立刻变了：

| 指标 | 改之前（全量） | 改之后（STRtree） |
|---|---|---|
| 一次查询 | O(n)，1.29M 个点全投影 | **0.02 ms** |
| 候选（8×，ne_10m） | 8,531（全部） | **13**（0.2%） |
| 候选（1×，中国省界） | 1,313 | **20**（1.5%） |
| 建索引 | — | 21（中国省界）/ 174 ms（ne_10m） |

"建一次 174 ms，省下来的每帧 300 ms"，这笔账在第一帧就赚回来了。

## 四、三个坑

### 4.1 包围盒的粒度

ne_10m 是 **4,595 个对象 / 8,531 个部件**：一个"国家"可能由好几块组成（岛屿）。按对象建索引，一个对象的所有岛共用一个包络，跨越半个地球；按部件建，每个岛一个包络。

第一版按对象插入，查询一切正常——**直到我拿 `--self` 自检时发现"候选数怎么是 4,595 而不是 8,531"**。原来漏的不是对象，是"对象里除第一块以外的部件"。

两种粒度的差别在画面上是隐形的（对象级粒度下，命中了就把整个对象重画一遍），但会让计数和悬停全部对不上。**结论：索引必须按"最小可绘单元"建，不是按"数据类"。**

### 4.2 索引里是投影坐标，payload 里是经纬度

`STRtree` 的节点存的是**投影后**的包络（因为查询矩形也是投影后算的）；而 `GeoPartHit.Points` 直接引用图层里那份**经纬度**列表（后续投影、命中测试都由调用方自己再做一遍）。

于是同一棵树里同时存在两套坐标系。第一版把两者混着比：

```csharp
// 错：拿经纬度去和投影矩形比
if (minX <= p.Lon && p.Lon <= maxX) ...
```

1× 线性投影下碰巧全对（投影是恒等），换成高斯-克吕格之后 X 变成米（1,474,075），而 `p.Lon` 还是 116——**一个都命中不了**。

**教训：一个数据结构里只应该有一种坐标。** 要放另一种，必须在字段名和注释里写明白它是哪一套。

### 4.3 失效点要穷举，不能靠记忆

索引不是数据，是数据的影子。它只依赖两样东西：`_layer`（点阵）和 `_settings`（投影）。这两样一变，包络就不在同一个坐标系里了。

而"变"的地方不止一处：

| 操作 | 代码位置 | 索引要不要重建 |
|---|---|---|
| 打开文件 | `MainWindow.xaml.cs:178` | 要 |
| 换源基准（基准转换拍平了部件） | `:257` | 要 |
| 换投影 | `:286` | 要 |

而且顺序也是正确性：换基准时 `_layer = RebuildTransformedLayer()` 必须写在"换finder"之前，否则旧 finder 手里握着的是已经被丢弃的那份图层。

为了证明这三处都接对了，验收里放了一个**故意不重建索引**的对照组：它必须被抓到。结果 8× 下差 19,541 像素、结构性差异 16,984、最大通道差 167——对照组被抓到了，另外七个 0 才算证据。

> [!WARNING] 一个从不失败的测试等于没测
> 验收工具里一定要有"把正确做法故意做错"的那一项。它会失败，你才知道其余各项的"通过"是有意义的。

## 五、怎么证明"没漏"

索引最大的风险不是慢，是**漏**——而且不报错，只是画面上少几个省。

裁判是真值（ground truth）：**对所有部件，把它的投影包络算出来，与查询矩形逐个比**（就是 `LinearFinder` 做的事）。然后：

| 判据 | 含义 | 结果 |
|---|---|---|
| 缺（漏给） | 真值里有、索引没给 | **0** |
| 多给 | 索引给了、真值里没有 | 允许（多给只是白画） |
| 非法 | 返回了不在图层里的对象 | **0** |

两个数据集、两种粒度、多个缩放档位，全部 0 缺、0 非法，候选率 0.2%–1.5%。

## 六、数据对比

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 8× 单帧（ne_10m） | 349 ms | **46 ms**（索引，7.5×） |
| 一次查询 | O(n) 全量 | **0.02 ms** |
| 1× 单帧（ne_10m，只有索引） | 807 ms | 807 ms（**没变**） |
| 建索引 | — | 174 ms（一次性） |
| 打开合计 | 3,764 ms | 3,638 ms |

最下面那行要单独说：**1× 全幅时索引一点用都没有**，因为整个地球都在视野里，候选就是全部。索引解决的是"放大之后还全扫"的问题；全幅时的成本要靠"少画/不画"。

## 七、可以复用的小结

> [!TIP] 引入空间索引的四步
> 1. **先写参照实现**。慢、简单、无状态、能给出正确答案。它是后面所有对照的基准，也是唯一能告诉你"漏没漏"的东西。
> 2. **索引按最小可绘单元建**，不按数据模型建。对象里可能有 5 个岛，那就是 5 个包络。
> 3. **一个数据结构里只放一种坐标**。混放的话，在"碰巧恒等"的投影下会全对，换个投影就全错。
> 4. **把失效点列成表，再逐条接上**，并在验收里放一个"故意不重建"的对照组。

下一篇处理那一半索引管不到的成本：1× 全幅时，明明所有对象都要画，为什么还要 807 ms —— 以及"框外的东西该在第几步被丢掉"。
